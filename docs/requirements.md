# EnergyCRM — опис платформи, функціональні вимоги та юзкейси

Nov 17, 2026 · @Michael

EnergyCRM — внутрішня веб-платформа для продажу електроенергії споживачам: вона веде базу клієнтів, угод, продуктів і споживання в одному місці, з воронками продажу та аналітикою на головному екрані.

## 1. Мета та контекст

**Мета.** Замінити розрізнені таблиці й нотатки єдиною системою, де видно, скільки клієнтів у роботі, на якому етапі кожна угода, скільки оплат уже надійшло і який обсяг електроенергії споживають клієнти.

**Користувачі.** Власник бізнесу (адмін) і менеджери з продажу (користувачі). Доступ закритий: самостійної реєстрації немає, акаунти створює лише адмін.

**Типи контактів.** Система працює з усім життєвим циклом: холодні контакти, теплі контакти, діючі клієнти. Історія спілкування, дані про споживання та про енергосистеми (облік, точки постачання) зберігаються при клієнті.

### Ключові принципи

- **Клієнт ≠ угода.** Картка клієнта описує людину або компанію. Картка угоди описує одну можливість продажу і живе у воронці. Один клієнт може мати кілька угод у різних воронках одночасно.
- **Воронки й етапи налаштовує адмін.** Жорстко заданих етапів немає: їх можна додавати, перейменовувати, переупорядковувати.
- **Продукт — довідник.** Опис, ціна й умови продукту задаються один раз і підтягуються в угоди.
- **Усе починається з ручного введення.** Клієнтів додають через таблицю й кнопку «Додати клієнта»; імпорт та інтеграції — наступні етапи.

### Глосарій

| Термін | Значення |
| --- | --- |
| Клієнт | Окрема особа або компанія, якій продається електроенергія; має контакти, історію і системи |
| Угода | Конкретна пропозиція продажу клієнту по одному продукту, що перебуває на етапі певної воронки |
| Воронка | Впорядкований набір етапів для одного типу продажу |
| Етап | Крок воронки (наприклад, «Перший контакт», «Пропозиція», «Договір», «Оплата») |
| Продукт | Тарифна пропозиція з описом, ціною та умовами |
| Споживання | Обсяг електроенергії клієнта за період (кВт·год) |
| Система | Об'єкт, де споживається електроенергія: точка обліку, адреса, потужність |
| Холодний / теплий контакт | Ступінь готовності до розмови: без попереднього зв'язку / вже виявив інтерес |

Додаткові терміни реєстру споживачів:

- **Менеджер** — користувач з роллю «Користувач», закріплений за клієнтами реєстру.
- **Відпрацьовано** — кількість контактів та угод менеджера за період (тлумачення уточнюється).
- **Група А / Б** — класифікація споживача за видом обліку та графіком споживання (див. відкриті питання).
- **Постачальник / розподіл** — хто постачає електроенергію клієнту і яка частка обсягу йде через кожного.
- **Генерація** — власне виробництво електроенергії у споживача (наприклад, СЕС).

## 2. Ролі та доступ

У системі дві початкові ролі: **Адмін** бачить і керує всім, **Користувач** — менеджер, таких користувачів може бути багато — працює зі спільним реєстром споживачів: бачить закріплених за ним клієнтів, веде їх угоди та налаштування споживача, але не міняє загальні налаштування. Адмін може редагувати права ролей в налаштуваннях.

| Дія | Адмін | Користувач |
| --- | --- | --- |
| Вхід за логіном і паролем | так | так |
| Створення / блокування користувачів | так | ні |
| Редагування ролей і прав | так | ні |
| Перегляд дашборду та аналітики | по всіх даних | лише по своїх клієнтах (за замовчуванням) |
| Налаштування воронок і етапів | так | ні |
| Редагування продуктів та цін | так | ні (лише перегляд) |
| Створення й редагування клієнтів | так | так |
| Створення та переміщення угод по етапах | так | так |
| Видалення клієнтів і угод | так | ні |
| Бачить усіх клієнтів | так | лише закріплених за ним або всіх (налаштовується для ролі) |

Ролі редаговані: адмін може змінювати рівні доступу вищенаведеної матриці та додавати нові ролі.

## 3. Модель даних

Центр моделі — звʼязок **Клієнт → угоди**: клієнт має кілька угод, кожна угода повʼязана з однією воронкою, одним етапом і одним продуктом. Споживання, оплати, комунікації та системи привʼязані до клієнта, а не до угоди.

| Сутність | Ключові поля | Звʼязки |
| --- | --- | --- |
| Користувач | Імʼя, логін (email), пароль (хеш), роль, статус (активний / заблокований) | Має роль; є відповідальним за клієнтів і угоди |
| Роль | Назва, набір прав (перегляд / створення / редагування / видалення по розділах) | 1 роль → багато користувачів |
| Клієнт | Тип (особа / компанія), назва або ПІБ, Телефон, email, місто, джерело, статус контакту (холодний / теплий / клієнт), відповідальний | Багато угод, систем, комунікацій, замірів споживання |
| Система | Тип обʼєкта, адреса, номер точки обліку, дозволена потужність (кВт), поточний постачальник | Власник — клієнт; має заміри споживання |
| Продукт | Назва, опис, ціна (грн/кВт·год), тарифна модель, термін дії, статус (активний / архівний) | Багато угод |
| Воронка | Назва, опис, статус (активна / архівна) | Має упорядковані етапи; багато угод |
| Етап | Назва, порядок, тип (в роботі / виграно / втрачено) | Належить одній воронці |
| Угода | Назва, клієнт, воронка, етап, продукт, очікуваний обсяг (кВт·год), сума, відповідальний, дата створення і закриття | Один клієнт, одна воронка, один етап, один продукт; багато оплат і нотаток |
| Оплата | Дата, сума, статус, угода, клієнт | Належить угоді |
| Споживання | Період (місяць), обсяг (кВт·год), система, джерело значення (вручну) | Належить системі та клієнту |
| Комунікація | Дата, канал (дзвінок / лист / зустріч / месенджер), короткий підсумок, автор | Належить клієнту (опційно угоді) |

### Доповнення: реєстр споживачів

Реєстр спільний для багатьох менеджерів: кожен клієнт закріплений за одним менеджером. До клієнта додаються налаштування споживача та нові сутності.

| Сутність / поле | Опис | Звʼязки |
| --- | --- | --- |
| Клієнт: закріплений менеджер | Хто відповідальний за клієнта; зміна менеджера зберігається в історії | Користувач (1 менеджер → багато клієнтів) |
| Система: група споживача | А або Б (почасовий або непочасовий облік, див. відкриті питання) | Властивість системи |
| Графік споживання | Для групи А — погодинні значення (кВт·год) по днях; для групи Б — місячні обсяги або типовий профіль | Належить системі; замінює простий запис «Споживання» для групи А |
| Розподіл через постачальника | Постачальник, період дії, частка обсягу (%); кілька записів на систему, сума часток — 100% | Належить системі; посилається на довідник постачальників |
| Генерація у споживача | Чи є (так / ні), тип (СЕС, вітрова, когенерація тощо), встановлена потужність (кВт), режим (для власного споживання / з віддачею в мережу) | Належить системі |
| Постачальник | Назва, який постачає або розподіляє електроенергію, контакти, статус | Довідник, який веде адмін |

## 4. Функціональні вимоги

Платформа складається з шести модулів. Кожна вимога має код (FR-…) для посилань у задачах і тестах.

### 4.1. Автентифікація та користувачі

- **FR-1.1** Вхід за логіном і паролем; неавторизований відвідувач бачить лише екран входу.
- **FR-1.2** Самостійної реєстрації немає: користувачів створює лише Адмін (імʼя, email, роль, тимчасовий пароль).
- **FR-1.3** Адмін може заблокувати користувача, скинути йому пароль і змінити роль.
- **FR-1.4** Після першого входу користувач мусить змінити тимчасовий пароль.
- **FR-1.5** Вихід з системи; автоматичний вихід після заданого часу неактивності.

### 4.2. Аналітика (головний екран)

Після входу користувач одразу бачить дашборд з ключовими показниками.

- **FR-2.1** Кількість клієнтів: всього та за статусом контакту (холодні / теплі / діючі).
- **FR-2.2** Угоди по етапах воронки: кількість і сума на кожному етапі, з вибором воронки.
- **FR-2.3** Оплати: скільки оплат відбулось та на яку суму за обраний період.
- **FR-2.4** Обсяг споживання клієнтами (кВт·год) за обраний період, з динамікою по місяцях.
- **FR-2.5** Фільтр періоду (тиждень, місяць, квартал, власний діапазон) для всіх показників; адмін додатково фільтрує за користувачем.

### 4.3. Воронки

- **FR-3.1** Список воронок і перемикання між ними; у відкритій воронці — канбан-дошка з етапами як колонками та картками угод.
- **FR-3.2** Переміщення картки угоди між етапами перетягуванням; кожне переміщення зберігається в історії (хто, коли, з якого етапу на який).
- **FR-3.3** Адмін створює, перейменовує і архівує воронки.
- **FR-3.4** Адмін додає, редагує, видаляє етапи та міняє їх порядок. Етап з угодами не видаляється, поки угоди не перенесено на інший етап.
- **FR-3.5** Кожен етап має тип: «в роботі», «виграно» або «втрачено»; саме це визначає, чи вважатиметься угода закритою.
- **FR-3.6** Картка угоди: клієнт, продукт, сума, очікуваний обсяг, відповідальний, оплати, нотатки, історія етапів.
- **FR-3.7** Створення угоди з картки клієнта або з воронки (з вибором існуючого клієнта або створенням нового).

### 4.4. Клієнти

- **FR-4.1** Таблиця всіх клієнтів з пошуком, фільтрами (статус контакту, відповідальний, місто, тип) і сортуванням.
- **FR-4.2** Кнопка «Додати клієнта» відкриває форму; обовʼязкові поля: тип, назва або ПІБ і хоча б один контакт (телефон або email).
- **FR-4.3** Перед збереженням система перевіряє дублікати за телефоном і email і попереджає про збіг.
- **FR-4.4** Картка клієнта має вкладки: профіль, угоди, спілкування, споживання, системи.
- **FR-4.5** Вкладка «Спілкування»: хронологія дзвінків, листів, зустрічей і нотаток; новий запис додається за кілька кліків.
- **FR-4.6** Вкладка «Споживання»: ручне внесення обсягу по місяцях для кожної системи.
- **FR-4.7** Вкладка «Системи»: обʼєкти клієнта з адресою, точкою обліку та потужністю.
- **FR-4.8** Зміна статусу контакту (холодний → теплий → клієнт) вручну; статус «клієнт» ставиться пропозицією, коли угода потрапляє в етап типу «виграно».

### 4.5. Продукти

- **FR-5.1** Список продуктів з назвою, ціною та статусом.
- **FR-5.2** Адмін створює й редагує продукт: опис, ціна, тарифна модель, термін дії, умови.
- **FR-5.3** Зміна ціни продукту не міняє суму вже створених угод; ціна заморожується в угоді на момент створення.
- **FR-5.4** Архівний продукт не пропонується для нових угод, але залишається в історичних.

### 4.6. Налаштування

- **FR-6.1** Керування користувачами та ролями (матриця прав з розділу 2).
- **FR-6.2** Довідники: джерела контактів, типи обʼєктів, канали комунікації, причини втрати угоди.
- **FR-6.3** Валюта (грн за замовчуванням), одиниці виміру (кВт·год) і часовий пояс (Київ).
- **FR-6.4** Журнал дій користувачів для адміна (див. розділ 6).

### 4.7. Реєстр споживачів та робота менеджерів

- **FR-7.1** Реєстр клієнтів є спільним; кожен клієнт має закріпленого менеджера. Адмін перезакріплює клієнтів по одному або масово (виділивши багато рядків у таблиці).
- **FR-7.2** Доступ до реєстру залежить від ролі: за замовчуванням менеджер бачить лише своїх клієнтів; адмін може дати ролі доступ до всього реєстру.
- **FR-7.3** Фільтри реєстру: менеджер, група А/Б, постачальник, наявність генерації, статус контакту; збережені фільтри для швидкого доступу.
- **FR-7.4** Облік відпрацьованого: для кожного менеджера за період — кількість контактів (дзвінки, листи, зустрічі), угод у роботі, виграних, втрачених, сума та обсяг виграних.
- **FR-7.5** Налаштування споживача в картці клієнта (на вкладці «Системи»): група А/Б, потужність, постачальник, генерація. Кожна зміна налаштувань зберігається в історії.
- **FR-7.6** Графіки споживання: для групи А — погодинні значення; для групи Б — місячні обсяги або типовий профіль. Введення вручну, відображення графіком за обраний період.
- **FR-7.7** Розподіл через постачальника: по системі можна задати кілька постачальників з частками обсягу та періодом дії; сума часток на одну дату дорівнює 100%, інакше збереження блокується.
- **FR-7.8** Генерація: прапорець «є генерація»; якщо так — обовʼязкові тип, потужність і режим. Для таких клієнтів аналітика показує спожиття з мережі окремо від власної генерації.
- **FR-7.9** Аналітика розрізає споживання за групою А/Б, постачальником і менеджером.
- **FR-7.10** Адмін керує довідником постачальників у «Налаштуваннях».

## 5. Юзкейси

У кожного юзкейсу — актор, передумова, основний сценарій, варіанти та результат.

### UC-1. Вхід адміна та перегляд аналітики

**Актор:** Адмін. **Передумова:** акаунт адміна створено й активний.

1. Адмін вводить логін і пароль.
2. Система перевіряє дані та відкриває головний екран «Аналітика».
3. Адмін бачить кількість клієнтів, розподіл угод по етапах, оплати та обсяг споживання.
4. Адмін міняє період і показники перераховуються.

**Варіанти:** невірний пароль — повідомлення без уточнення, що саме невірно; після 5 невдалих спроб вхід тимчасово блокується; немає даних — порожній стан з підказкою «додайте першого клієнта». **Результат:** адмін одразу бачить стан бізнесу.

### UC-2. Реєстрація користувача

**Актор:** Адмін. **Передумова:** адмін увійшов у систему.

1. Адмін відкриває «Налаштування → Користувачі» і натискає «Додати».
2. Вказує імʼя, email і роль (Адмін або Користувач).
3. Система генерує тимчасовий пароль і показує його адміну один раз.
4. Адмін передає дані для входу користувачеві; при першому вході такий користувач міняє пароль.

**Варіанти:** email вже є в системі — помилка, акаунт не створюється. **Результат:** у системі є новий користувач з потрібною роллю.

### UC-3. Налаштування продукту

**Актор:** Адмін.

1. Адмін обирає розділ «Продукти» і натискає «Додати продукт».
2. Вносить назву, опис, ціну (грн/кВт·год), тарифну модель і термін дії.
3. Зберігає — продукт зʼявляється в списку та доступний для нових угод.

**Варіанти:** ціна ≤ 0 — помилка валідації. **Результат:** є продукт, який можна пропонувати клієнтам.

### UC-4. Налаштування воронки та етапів

**Актор:** Адмін.

1. Адмін відкриває «Воронки» і створює воронку (наприклад, «Продаж бізнесу»).
2. Додає етапи в потрібному порядку: «Новий контакт», «Розмова», «Пропозиція», «Договір», «Оплата».
3. Для кінцевих етапів задає тип «виграно» і «втрачено».
4. Перетягує етапи, щоб змінити порядок.

**Варіанти:** спроба видалити етап з угодами — система пропонує перенести їх на інший етап. **Результат:** воронка готова до роботи.

### UC-5. Додавання клієнта

**Актор:** Адмін, Користувач. **Передумова:** є хоча б одна активна воронка та продукт.

1. В розділі «Клієнти» користувач натискає «Додати клієнта».
2. Заповнює форму: тип, назва або ПІБ, контакти, джерело, статус контакту.
3. Система перевіряє дублікати за телефоном і email.
4. Користувач зберігає — клієнт зʼявляється в таблиці.
5. Опційно одразу створює угоду (→ UC-6).

**Варіанти:** знайдено дублікат — користувач обирає: відкрити існуючого, обʼєднати або все одно зберегти. **Результат:** клієнт у базі з заповненим профілем.

### UC-6. Створення другої угоди для існуючого клієнта

**Актор:** Адмін, Користувач. **Передумова:** клієнт уже є, у нього може бути інша активна угода.

1. Користувач відкриває картку клієнта, вкладку «Угоди».
2. Натискає «Нова угода», обирає воронку та продукт.
3. Система створює угоду на першому етапі обраної воронки.

**Результат:** один клієнт їде по кількох воронок одночасно, дублювання профілю не потрібне.

### UC-7. Ведення угоди по воронці до оплати

**Актор:** Користувач. **Передумова:** угода створена і була заповнена базова інформація.

1. Користувач дзвонить клієнту і додає запис у «Спілкування».
2. Вносить споживання та дані системи клієнта.
3. Перетягує картку угоди на етап «Пропозиція», потім «Договір».
4. Після отримання коштів додає оплату і переносить угоду на етап типу «виграно».

**Варіанти:** клієнт відмовився — угода переходить у «втрачено» з обовʼязковою причиною. **Результат:** угода закрита, аналітика оновлена.

### UC-8. Пошук клієнта та перегляд історії

**Актор:** Адмін, Користувач.

1. Користувач вводить імʼя, телефон або email у пошуку таблиці клієнтів.
2. Додатково застосовує фільтр (наприклад, «теплі контакти»).
3. Відкриває картку та бачить угоди, спілкування, споживання й системи.

**Результат:** користувач має повний контекст перед розмовою.

### UC-9. Перезакріплення клієнтів між менеджерами

**Актор:** Адмін. **Передумова:** є кілька менеджерів і клієнти в реєстрі.

1. Адмін відкриває реєстр і фільтрує по менеджеру (наприклад, тому, що звільняється).
2. Виділяє потрібні рядки і обирає нового менеджера.
3. Система перезакріплює клієнтів і їх активні угоди і записує зміну в журнал.

**Результат:** новий менеджер бачить переданих клієнтів і їх історію, старий — не бачить.

### UC-10. Налаштування споживача: група, постачальник, генерація

**Актор:** Менеджер. **Передумова:** клієнт закріплений за менеджером або у менеджера є доступ до всього реєстру.

1. Менеджер відкриває картку клієнта, вкладку «Системи», обирає систему.
2. Вказує групу А або Б і потужність.
3. Додає постачальника і частку обсягу; якщо постачальників кілька — частки мають дати в сумі 100%.
4. Відмічає, чи є у споживача генерація; за «так» заповнює тип, потужність, режим.

**Варіанти:** частки не дорівнюють 100% — помилка без збереження. **Результат:** налаштування споживача збережені з історією змін.

### UC-11. Внесення графіка споживання

**Актор:** Менеджер. **Передумова:** у системи вказана група А або Б.

1. Менеджер відкриває вкладку «Споживання» системи.
2. Для групи А вносить погодинні значення за добу; для групи Б — місячний обсяг.
3. Система показує графік і оновлює аналітику обсягу.

**Результат:** графік споживання доступний в картці клієнта та в загальній аналітиці.

### UC-12. Звіт по відпрацьованому по менеджерах

**Актор:** Адмін.

1. Адмін обирає період у «Аналітиці».
2. Обирає розріз «По менеджерах».
3. Бачить для кожного менеджера контакти, угоди в роботі, виграні й втрачені угоди, суму і обсяг.

**Результат:** адмін бачить, хто скільки відпрацьовує.

## 6. Нефункціональні вимоги

База містить персональні дані та комерційну інформацію, тому найважливіші вимоги — безпека й контроль доступу.

| Код | Категорія | Вимога |
| --- | --- | --- |
| NFR-1 | Безпека | Паролі зберігаються лише у вигляді хешу; мінімум 12 символів; зʼєднання лише по HTTPS |
| NFR-2 | Безпека | Перевірка прав ролі відбувається на сервері, а не лише в інтерфейсі |
| NFR-3 | Безпека | Обмеження спроб входу (5 невдалих → тимчасове блокування) та захист від типових веб-атак |
| NFR-4 | Персональні дані | Дані клієнтів (ПІБ, телефон, адреса) зберігаються за вимогами законодавства про захист персональних даних; можливість видалити або анонімізувати клієнта за запитом |
| NFR-5 | Аудит | Журнал дій: хто, коли і що змінив (клієнти, угоди, ролі, продукти, воронки); журнал не редагується |
| NFR-6 | Продуктивність | Відкриття сторінки та таблиці клієнтів до 2 с при базі до 10 000 клієнтів; пошук до 1 с |
| NFR-7 | Надійність | Щоденне резервне копіювання бази та можливість відновлення |
| NFR-8 | Зручність | Українська мова інтерфейсу; коректна робота на ноутбуку та на планшеті |
| NFR-9 | Цілісність даних | Валідація полів (email, телефон, суми, обсяги); заборона видалення клієнта з активними угодами без підтвердження |

Додатково для спільного реєстру:

- **NFR-10** Права доступу до клієнтів перевіряються на сервері на рівні запису: менеджер не може отримати чужого клієнта навіть через пряме посилання.
- **NFR-11** Графіки групи А зберігаються як погодинні значення (до 8 760 значень на рік на одну систему) і відображаються без помітного сповільнення.
- **NFR-12** Зміни налаштувань споживача, закріплення менеджера та часток постачальників зберігаються з датою й автором.

## 7. MVP, наступні етапи та відкриті питання

MVP покриває весь сценарій з опитування власника: вхід, ролі, продукт, воронки з етапами, ручне додавання клієнтів, угоди та аналітика. Інше — після.

### MVP

- Автентифікація, ролі «Адмін» і «Користувач», реєстрація користувачів адміном.
- Продукти: створення та редагування.
- Воронки та етапи: налаштування, канбан-дошка, перетягування угод.
- Клієнти: таблиця, додавання вручну, картка зі спілкуванням, споживанням і системами.
- Угоди: створення, кілька угод на клієнта, історія етапів, оплати.
- Аналітика: клієнти, угоди по етапах, оплати, споживання.

* Спільний реєстр з багатьма менеджерами, закріплення клієнтів, облік відпрацьованого по менеджерах.
* Налаштування споживача: група А/Б, постачальник з частками, генерація; графіки споживання (введення вручну).

### Після MVP

- Імпорт клієнтів з Excel/CSV та експорт таблиць.
- Нагадування та задачі по угодах (наступний дзвінок).
- Інтеграції: телефонія, месенджери, пошта, форми лідів з сайту.
- Автоматичне отримання даних споживання з обліку.
- Документи та шаблони: комерційні пропозиції, договори.
- Додаткові ролі та гранулярні права; поширена аналітика по менеджерах і джерелах.

### Відкриті питання

- [ ] Підтвердіть: менеджер бачить лише своїх клієнтів і аналітику по них, а повний реєстр — лише за дозволом адміна?
- [ ] Чи є більше ніж дві ролі у першому релізі (наприклад, переглядач)?
- [ ] Чи відповідає угода лише за один продукт, чи в одній угоді може бути кілька?
- [ ] Як рахується сума угоди: за очікуваним річним обсягом × ціну чи вводиться вручну?
- [ ] Клієнти — фізичні особи, бізнес чи обидва типи? Які поля обовʼязкові (наприклад, ЄДРПОУ, EIC-код точки обліку)?
- [ ] Чи потрібна будь-яка інтеграція з оплатами, чи оплати вносяться вручну?
- [ ] Що значить «оплата» в аналітиці: аванс, рахунок за місяць чи обидва?
- [ ] Чи надані числа в нефункціональних вимогах (12 символів пароля, 5 спроб входу, 2 с, 10 000 клієнтів) підходять? Це мої припущення, а не ваші дані.

* [ ] Як саме визначаються групи А і Б у вашому процесі? Я припустив: А — з погодинним обліком, Б — без нього.
* [ ] Що означає «скільки відпрацьовано»: активність менеджерів (контакти, угоди) чи обсяг уже поставленої електроенергії? Я реалізував перше (FR-7.4); друге вже є в споживанні.
* [ ] Що саме означає «розподіл через постачальника»: з якого постачальника скільки обсягу йде, чи розподіл між кількома постачальниками? Я реалізував частки обсягу по постачальниках.
* [ ] Чи потрібні для генерації додаткові параметри: «зелений» тариф, обсяг віддачі в мережу?
* [ ] Чи потрібен імпорт графіків споживання з файлів оператора, чи достатньо ручного введення на старті?
